# Reliable CDC for LOB-heavy tables without primary keys using AWS Lambda

This sample demonstrates a narrowly scoped CDC pattern for an Amazon RDS for SQL Server table with large `nvarchar(max)` values and no enforced primary key. The pattern requires a stable, non-null business identifier that uniquely identifies each logical row; this sample calls it `SourceRecordID`.

AWS DMS performs the initial full load. AWS Lambda then reads SQL Server CDC changes and applies them to Amazon Aurora PostgreSQL-Compatible Edition.

> This sample is specific to this migration scenario. It is not a general replacement for AWS DMS CDC.

## Critical prerequisite

Before using the pattern, run `sql/01-source-prerequisites.sql`. `SourceRecordID` must be non-null and unique. Resolve any violations before continuing. The target enforces the same invariant with a unique key.

## Processing model

1. Establish a valid CDC migration-start boundary before or in coordination with the AWS DMS full load.
2. Retain CDC history while the baseline is copied.
3. Seed `cdc_sync.cdc_state.last_to_lsn` to the LSN immediately preceding that established boundary.
4. Configure Lambda reserved concurrency to 1.
5. For every invocation, calculate `from_lsn = sys.fn_cdc_increment_lsn(last_to_lsn)` and use `sys.fn_cdc_get_max_lsn()` as the complete window endpoint.
6. Stop if `from_lsn` is older than `sys.fn_cdc_get_min_lsn(capture_instance)`.
7. Read the complete inclusive window with `cdc.fn_cdc_get_all_changes_<capture_instance>(..., N'all')`, ordered by `__$start_lsn, __$seqval`.
8. Reduce multiple changes for a `SourceRecordID` to its final ordered change.
9. Apply final DELETEs or UPSERTs to Aurora.
10. Update `last_to_lsn` in the same Aurora transaction as the target data changes.

The invariant is:

```text
last_to_lsn = last LSN successfully applied
increment(last_to_lsn) = first LSN still to process
```

The migration runbook must choose `migration_start_lsn` first. `sys.fn_cdc_decrement_lsn()` only derives the preceding checkpoint; it does not choose the migration boundary.

## Configuration

The Lambda function expects `SOURCE_SECRET_ID`, `TARGET_SECRET_ID`, `CDC_CAPTURE_INSTANCE`, `STATE_CAPTURE_INSTANCE`, and `TARGET_TABLE`.

Optional overrides are `ODBC_DRIVER` (default `ODBC Driver 18 for SQL Server`) and `PGSSLMODE` (default `verify-full`).

`pyodbc` and the PostgreSQL client have native deployment considerations. Read `DEPLOYMENT.md` before packaging the Lambda function.

Use AWS Secrets Manager for credentials. Configure network access from Lambda to both databases. Use encrypted database connections with certificate validation according to your organization's policy. Use least-privilege IAM and database permissions.

Configure Lambda **reserved concurrency to 1** so only one worker applies a checkpoint stream at a time. A throttled invocation must not advance the checkpoint; event delivery/retry behavior depends on the invoking service and its configuration.

## CDC operation handling

This sample uses `N'all'`. It processes DELETE (`1`), INSERT (`2`), and UPDATE after-image (`4`). If you change to `all update old`, operation `3` is the UPDATE before-image and must not be used as the final target state.

The worker reduces an ordered CDC window to one final change per `SourceRecordID`. This prevents duplicate keys in a single PostgreSQL `ON CONFLICT` statement and preserves the final logical state when the same key changes multiple times in one window.

## LOB and collation testing

Test representative `nvarchar(max)` data, including multilingual and supplementary characters. Also test comparison, sorting, case-sensitivity, and uniqueness behavior because SQL Server and PostgreSQL collation behavior can differ.

## Schema changes

Treat source DDL changes as a separate operational event. Do not assume a source schema change automatically becomes part of the existing CDC capture configuration or Lambda mapping.

## Cleanup

Disable the Lambda trigger before removing the function or CDC state. Remove sample-only resources and secrets when no longer needed. Do not remove SQL Server CDC history or the checkpoint until you are certain no catch-up or recovery is required.
